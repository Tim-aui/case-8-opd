## 2. ПР 1–2 · Vision продукта

### 2.1. Ограничения и допущения со стороны 1С

**Ограничения** (заданы заранее, менять не можем):

| Код | Ограничение |
|---|---|
| О-1 | Платформа «1С:Предприятие 8.3» (учебная версия), собственная конфигурация без снятия типовых объектов с поддержки |
| О-2 | Данные поступают **только из CSV-файлов** `books.csv`, `readers.csv`, `loans.csv`. Интеграции с АБИС (ИРБИС, «1С:Библиотека» и др.) нет |
| О-3 | Отчёт «Просрочки» строится на **СКД** (система компоновки данных) |
| О-4 | Выгрузка в CSV делается программно (через запись текста). Табличный документ СКД штатно сохраняется в XLSX/MXL/PDF, но **не в CSV** |
| О-5 | Учебная база в файловом режиме: рассчитана примерно на 5–10 одновременных пользователей (по лекции 2) |
| О-6 | Две роли 1С: «Библиотекарь» и «Администратор»; права задаются ролями, без RLS (ограничения на уровне записей) |

**Допущения** (на что полагаемся; если неверно — пересматриваем):

| Код | Допущение |
|---|---|
| Д-1 | CSV в кодировке UTF-8, первая строка — заголовки, даты в формате `ГГГГ-ММ-ДД` |
| Д-2 | Идентификаторы `book_code`, `reader_id`, `loan_id` уникальны и **не меняются** между выгрузками — на этом держится идемпотентный импорт |
| Д-3 | Единица выдачи — запись `books.csv` с кодом `book_code`; правило «одна активная выдача» действует на `book_code` |
| Д-4 | Активная выдача — строка `loans.csv` с `return_date = NULL` (пусто) |
| Д-5 | Определение просрочки — **по кейсу**: выдача просрочена, если `return_date = NULL` и `today > due_date` **или** `return_date > due_date`. Отсюда два статуса: **«просрочена»** (активная, `return_date = NULL`, `today > due_date`) и **«возвращена с просрочкой»** (`return_date > due_date`). Отчёт «Просрочки» и CSV показывают обе группы с колонкой `status`; KPI — только по активным (решение D-9) |
| Д-6 | Одна библиотека, без филиалов и без штрафов |
| Д-7 | Объём набора T1: **400–800 выдач, 200–300 книг, 120–200 читателей** (по замечанию 3 тимлида). Порог производительности проверяем на T1 и с запасом на 10 × T1 |

### 2.2. Реализуемость пунктов «входит» на 1С в сроки курса

| Пункт «входит» | Реализуемо? | Замечание 1С |
|---|---|---|
| Выдача и возврат книги, статусы выдач (выдана / возвращена / **просрочена** / **возвращена с просрочкой**) | **Да** | Выдача и возврат — документы. Статусы не хранятся, а вычисляются по датам (A-08-2): «возвращена с просрочкой» — `return_date > due_date`; после возврата даты не меняются, поэтому этот статус постоянен. «Просрочена» для активной выдачи **не храним**, а вычисляем на дату отчёта, иначе нужен регламентный пересчёт статусов каждую ночь (см. A-08-2) |
| Проверка «одна активная выдача на экземпляр» | **Да** | Проверка при проведении документа «Выдача» + управляемая блокировка по экземпляру, чтобы два библиотекаря не выдали один экземпляр одновременно |
| Отчёт «Просрочки» (≤ 2 сек на T1) с полями кейса `reader_id, fio, book_code, title, days_overdue` + `status` | **Да** | СКД с параметром «Дата отчёта». Две группы статусов с колонкой `status` (D-9). На T1 (400–800 выдач) порог выполняется с большим запасом; индекс по сроку возврата и отбор в запросе, а не в компоновке — задел на рост |
| Импорт CSV `books / readers / loans` | **Да** | Схема задана кейсом (§3.2). Порядок загрузки: readers → books → loans |
| Повторный импорт без дублей | **Да** | Ключ — `loan_id` (и `book_code`, `reader_id` для справочников). Запись «найти по ключу → обновить, иначе создать» |
| Экспорт отчёта в CSV (минимум `reader_id, book_code, days_overdue` — требование кейса) | **Да, с замечанием** | Штатной выгрузки СКД в CSV нет — пишем отдельную процедуру (О-4). Формат выгрузки = формат `golden/overdue.csv`, иначе сравнение «расхождение = 0» не автоматизировать |

| Сверка отчёта с `golden/overdue.csv` (расхождение 0) | **Да** | Эталон агрегирован по читателю (Д-8: `reader_id, loans_total, overdue_cnt, overdue_days_sum`). Выгрузка сводится к этому формату группировкой СКД по `reader_id` — см. §3.3, «Сверка с эталоном» |

Не входит и на 1С в хакатоне 1 не делаем: штрафы, уведомления читателям, интеграция с АБИС, кабинет читателя, HTTP-сервис для BI (только «в перспективе» на C4).

### 3.2. Дополнение UC-08-3 «Импортировать данные»

**Формат файлов** (схема из кейса 8):

| Файл | Колонки | Ключ |
|---|---|---|
| `readers.csv` | `reader_id, fio, group` | `reader_id` |
| `books.csv` | `book_code, title, author, year, udk` | `book_code` |
| `loans.csv` | `loan_id, reader_id, book_code, issue_date, due_date, return_date` (`return_date` пусто = NULL — не возвращена) | `loan_id` |

**Проверки, которые делает система** (до записи в базу, по всему пакету):

| № | Проверка | Что считается ошибкой | Реакция |
|---|---|---|---|
| П-1 | Формат файла | Не UTF-8, нет обязательной колонки, файл пуст | Исключение E-1: файл не загружается целиком |
| П-2 | Типы и обязательность | Пустой ключ, дата не в формате `ГГГГ-ММ-ДД` | Строка отклоняется, попадает в протокол |
| П-3 | Уникальность ключа внутри файла | Два одинаковых `loan_id` (`book_code`, `reader_id`) в одном файле с разными данными | Обе строки отклоняются |
| П-4 | **Ссылочная целостность** | `loans.book_code` нет ни в `books.csv`, ни в базе; то же для `loans.reader_id` | Строка выдачи отклоняется |
| П-5 | **Порядок дат** | `issue_date > due_date`; `return_date` заполнена и `return_date < issue_date`; дата выдачи в будущем | Строка отклоняется |
| П-6 | **Одна активная выдача на экземпляр** | У одного `book_code` больше одной выдачи с `return_date = NULL` (в файле или с учётом уже загруженных); пересекающиеся периоды выдачи одного экземпляра | Отклоняются конфликтующие строки, кроме уже загруженной |

> **Замечание по П-5 (нужно подтвердить).** В кейсе правило записано так: **«если return_date задана — due_date ≤ return_date»** (в ТЗ по ролям — `issue ≤ due ≤ return`). Если читать буквально, система отклонит каждую книгу, сданную **раньше** срока (`return_date < due_date`), хотя это нормальная ситуация; к тому же такое правило противоречит определению просрочки из того же кейса (`return_date > due_date` — отдельный статус, значит `return_date ≤ due_date` тоже допустим). Предлагаем правило: `issue_date ≤ due_date` и, если `return_date` задана, `issue_date ≤ return_date`; `return_date > due_date` допустим — это статус «возвращена с просрочкой». Нужно подтвердить.

**Основной поток** (со стороны 1С):

1. Администратор открывает «Импорт данных» и выбирает файлы `readers.csv`, `books.csv`, `loans.csv`.
2. Система проверяет формат файлов (П-1).
3. Система проверяет строки (П-2…П-6) в порядке readers → books → loans.
4. Система записывает корректные строки: одна транзакция на файл.
5. Система показывает протокол с четырьмя счётчиками: **создано / обновлено / пропущено (дубль) / отклонено** (с причиной и номером строки). Каждая строка файла попадает ровно в один счётчик: сумма = числу прочитанных строк.

**Альтернативный поток А-1 — повторный импорт (идемпотентность по D-7, README §3; R → A-08-1).**

3а. Строка с таким `loan_id` уже есть в базе. Система сравнивает строку CSV с выдачей в 1С и выбирает ровно одну из четырёх веток:

| Ветка | Условие | Действие системы | Счётчик |
|---|---|---|---|
| D-7.1 | Все поля совпадают (в том числе `return_date`: пусто = пусто или дата = дата) | Ничего не меняет | **пропущено** |
| D-7.2 | В CSV появилась `return_date`, а выдача в 1С **активна**; остальные поля совпадают | Оформляет документ «Возврат книги» с датой `return_date` (см. ниже) | **обновлено** |
| D-7.3 | В 1С возврат **уже оформлен**, а в CSV `return_date` пусто (файл старше базы) | Ничего не меняет: данные 1С свежее | **пропущено** |
| D-7.4 | Любое другое расхождение: другой `reader_id`, `book_code`, `issue_date`, `due_date`; разные даты возврата в CSV и 1С; `return_date` не проходит П-5 | Не меняет базу, строку в протокол с причиной | **отклонено** |

Новая `loan_id` (её нет в базе) и строка корректна → создаётся выдача (и возврат, если `return_date` задана) → **создано**.

**Повтор того же файла:** после первого прогона все выдачи из файла уже есть в базе, а их возвраты оформлены — все строки попадают в D-7.1 (или D-7.4, если отклонялись и в первый раз). Итог: **создано = 0, обновлено = 0**, дублей нет. Справочники `book_code`, `reader_id` работают так же: совпало → пропущено, новая запись → создано, расхождение → отклонено.

**Реализуемость закрытия выдачи из CSV (D-7.2) — подтверждаю, да.** Как это сделано в 1С:

* Обработка импорта создаёт документ «Возврат книги» программно, по той же форме заполнения, что и при ручном возврате: основание — выдача с этим `loan_id`, дата возврата = `return_date` из CSV.
* Документ проводится через **те же проверки проведения**, что и ручной возврат (выдача активна, `return_date ≥ issue_date`, дата не в будущем). Отдельной «обходной» записи в регистр нет — выдача закрывается движениями документа «Возврат», поэтому отчёт и статусы считаются одинаково для ручных и импортированных возвратов.
* Отдельно статус записывать не нужно: он вычисляется по датам (A-08-2), и выдача с `return_date > due_date` сразу показывается как «возвращена с просрочкой».
* Трассируемость (D-8): автор документа — пользователь, запустивший импорт; в комментарии — «Создан импортом, файл loans.csv, строка N»; запись в журнале регистрации.
* Ограничение: проведение задним числом (дата возврата из CSV раньше текущей) разрешено роли «Администратор» для импорта; дату запрета изменения данных в MVP не используем.
* Атомарность и ограничение платформы: в 1С ошибка внутри транзакции делает **всю** транзакцию неуспешной («В данной транзакции уже происходили ошибки»), поэтому «отклонить строку и продолжить» внутри транзакции нельзя. Решение: все проверки (V-1…V-6, ветки D-7, условия проведения «Возврата») выполняются **до** записи, без транзакции; в транзакцию файла попадают только прошедшие проверку строки. Если при записи всё же произошла техническая ошибка — откатывается весь файл (NFR-6), повторный запуск безопасен благодаря D-7.

**Альтернативный поток А-2 — часть строк с ошибками.**

3б. Ошибочные строки (V-2…V-6 и ветка D-7.4) не загружаются, корректные загружаются. Протокол можно сохранить в файл, чтобы исправить исходные данные и загрузить снова (повтор безопасен благодаря А-1).

**Исключение E-1 — файл не прошёл проверку формата.** Импорт прерывается, база не меняется, администратор видит сообщение с причиной («В файле loans.csv нет колонки due_date»). Ошибка пишется в журнал регистрации.

**Исключение E-2 — сбой при записи** (например, база заблокирована). Транзакция по файлу откатывается целиком: либо файл записан полностью, либо не записан совсем. Сообщение пользователю и запись в журнал регистрации.

**Постусловие:** данные загружены без дублей, у каждой выдачи есть существующие книга и читатель, у каждого экземпляра не больше одной активной выдачи; доступен протокол загрузки.

### 3.3. Дополнение UC-08-5 «Экспортировать CSV»

**Предусловие:** пользователь с ролью «Библиотекарь» или «Администратор» сформировал отчёт «Просрочки» на дату `D`.

**Проверки и правила:**

| № | Правило |
|---|---|
| Э-1 | Выгружаются ровно те строки, что видны в отчёте на дату `D` (с теми же отборами) — число строк в файле = числу строк отчёта |
| Э-2 | Детальная выгрузка: UTF-8, разделитель как в `golden/overdue.csv`, даты `ГГГГ-ММ-ДД`, сортировка по `reader_id`, затем `loan_id` |
| Э-3 | **Требование кейса:** отчёт содержит `reader_id, fio, book_code, title, days_overdue`; CSV — **как минимум** `reader_id, book_code, days_overdue`. По D-9 добавляем `status`. Колонки детальной выгрузки: `loan_id, reader_id, fio, book_code, title, due_date, return_date, status, days_overdue`. `days_overdue`: для «просрочена» = `D − due_date`; для «возвращена с просрочкой» = `return_date − due_date` (целое > 0) |
| Э-5 | По D-9 в выгрузку попадают обе группы: `status = просрочена` (`return_date = NULL`, `D > due_date`) и `status = возвращена с просрочкой` (`return_date > due_date`). KPI в шапке отчёта — только по `просрочена` |
| Э-4 | Имя файла содержит дату отчёта: `overdue_ГГГГ-ММ-ДД.csv` |

**Основной поток:** пользователь нажимает «Выгрузить в CSV» → выбирает место сохранения → система формирует файл → показывает «Выгружено N строк в файл …».

**Альтернативный поток А-1 — просрочек нет.** Система создаёт файл только со строкой заголовков и сообщает «Просрочек на дату D нет». Пустой файл с заголовком сравнивается с эталоном так же, как непустой.

**Исключение E-1 — файл не удалось записать** (нет прав на папку, файл открыт в Excel). Сообщение «Не удалось сохранить файл: <причина>. Закройте файл или выберите другую папку», запись в журнал регистрации; отчёт остаётся на экране.

**Сверка с эталоном (Д-8).** `golden/overdue.csv` агрегирован по читателю: `reader_id, loans_total, overdue_cnt, overdue_days_sum`. Детальная выгрузка сводится к нему так:

| Колонка эталона | Как получается из данных 1С на дату `D` |
|---|---|
| `reader_id` | Группировка по читателю |
| `loans_total` | Количество **всех** выдач читателя с `issue_date ≤ D` (любой статус) |
| `overdue_cnt` | Количество выдач читателя со статусом «просрочена» **или** «возвращена с просрочкой» — это определение просрочки из кейса |
| `overdue_days_sum` | Сумма `days_overdue` по этим выдачам (правило расчёта — Э-3) |

* В 1С это второй вариант отчёта «Просрочки» — «Сводка по читателям» (группировка СКД по `reader_id` с ресурсами КОЛИЧЕСТВО и СУММА) — и кнопка «Выгрузить для сверки» → `overdue_by_reader_ГГГГ-ММ-ДД.csv` в формате и порядке колонок эталона, сортировка по `reader_id`.
* `loans_total` берётся по **всем** выдачам, поэтому сводку строим по таблице выдач, а не по уже отфильтрованной детальной выгрузке.
* Сверка: оба файла сортируются по `reader_id` и сравниваются по 4 колонкам. Расхождение = строка есть только в одном файле **или** отличается хотя бы одно число. Цель — 0.
* Дата `D` для сверки = дата, на которую построен эталон (фиксированный параметр, не текущая дата).
* Проверить по эталону: попадают ли в него читатели с `overdue_cnt = 0` (если да — сводка строится по всем читателям с выдачами; если нет — только с `overdue_cnt > 0`).

**Постусловие:** CSV-файл с просрочками на дату `D` сохранён; сводка по читателям на эталонную дату совпадает с `golden/overdue.csv`, 0 расхождений.
